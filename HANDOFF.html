Runtime architecture (as of Phase 2)

  • Image: multi-stage Dockerfile. Builder runs npm ci + next build; the final stage carries only the Next standalone output + .next/static + public + an esbuild-bundled migrate.mjs. No devDeps, no toolchain, no src/. Base node:24-slim pinned by digest.
  • Least privilege: runs as USER node (uid 1000); code is root-owned read-only, only /app/data is writable.
  • Startup: node migrate.mjs && node server.js (no npm at runtime). The prod compose wraps it with a guard that aborts if BUDGETSPIN_AUTH_SECRET is unset.
  • Routing: Traefik labels on the app service; private hostname budget-spin.ts.local over Tailscale; no host port published.
  • Data: SQLite at /app/data/budgetspin.sqlite in volume budgetspin-prod-data; created/seeded by migrate() on first start; persists across deploys. The image contains no database (see OBS-008).

Image 1.75 GB → 421 MB (−76%), non-root, reproducible (digest pin + npm ci). Verified: whoami = node, migrate.mjs runs standalone, GET /login 200.

App capabilities

Auth

  • Single local user mdaneri; legacy local-user data migrates to it. First login initializes the password (stored as hash + salt).
  • Session as a signed HTTP-only cookie; credential comparison via timingSafeEqual (src/auth/session.ts); routes protected by proxy.ts; logout in the header.
  • 2FA is modeled for later but not enforced yet.
  • API auth model: every /api/* route goes through proxy.ts; the allow/deny decision is decideAccess in src/auth/access-policy.ts (default closed). Without a session a page redirects to /login?next=… and an API path gets 401 JSON. Only /api/ingest/itau and /api/ingest/splitwise skip the session (exact path match) because they check their own bearer token. /api/fx-rate also checks the session itself.
  • Form and login errors travel as fixed codes in ?error= and pages map them to fixed text (src/actions/error-codes.ts); the query value is never rendered.

Finance

  • Recurring income (incl. custom recurrences, e.g. aguinaldo) and recurring expenses (committed vs optional, custom recurrences).
  • Expense categories and families/groups.
  • Dashboard: income, committed/optional spend, net, category and family breakdown, six-month projection.
  • Plans with target date/amount/currency, sub-purchases/checklist, and calculation detail (included months).
  • Currency: amounts display in their source currency and can be clicked to cycle; FX stored per record, with automatic lookup in forms.

Automatic categorisation

Imported bank purchases and Splitwise expenses get a category on arrival; there is no suggestion queue. The owner changes it on /transactions or /splitwise.

  • Lookup order (automaticImportCategory): exact-description rule → merchant rule → the expense category "Other". A rule pointing at an inactive category is ignored. Transfers and Splitwise payments get no category.
  • Merchant key (src/finance/merchant-key.ts, pure function): input capped at 256 characters, Unicode NFKC, lower-case, split into word tokens (punctuation and * are separators). Drops one trailing letters-only word when it follows a token with digits (location after an id, e.g. …*TEST*00 ABCDE), then trailing tokens containing digits (store/branch numbers, reference or terminal ids). Fewer than 3 characters or no letter → no merchant lookup.
  • Learning (rememberImportCategory): only an explicit category change by the owner writes rules — one for the exact description, one for the merchant key. Last choice wins. Rules never rewrite categories stored on other rows, neither for exact nor for merchant matches; they only apply to rows created later (or to bank rows still without a category when migrate() runs).
  • Storage: same table, no schema change. Merchant rules use the key "\tmerchant:" + merchantKey; exact keys are trimmed, so they never start with a tab and the two kinds cannot collide.

Limits

No place-name list, so a trailing location word is removed only in the "id then one word" shape; MERCADO X CENTRO and MERCADO X NORTE stay distinct. A name ending in a number after a word collapses to the word (CAFE 1900 → cafe), which can merge unrelated merchants with a short shared prefix. Processor prefixes (PROCESSOR*SHOP) are not stripped, so each shop behind one processor is learned separately. A forged notice (see the trust boundary below) cannot create rules, but it is filed by them.

Activation

Two mutually exclusive ways to schedule the trigger routes: the Compose profiles ingest / splitwise-ingest (token in INGEST_TOKEN), or scripts/activate-sync.py (token file, containers outside Compose; it refuses to run if the app has INGEST_TOKEN set). Pick one. Procedures in RUNBOOK; unifying them is MEJ-005.

Trust boundary — bank e-mails are not authenticated

A notice is accepted as a bank notice when its single From address is in the bank's domain and its subject matches a known pattern (isItauAviso, isItauTransfer). There is no DKIM, DMARC or Authentication-Results check anywhere in src/. Anyone able to deliver mail to the mailbox can forge such a notice; it would be imported as pending and counted in observed spending until someone discards it on /transactions. Mailbox authentication does not change this: it authenticates access to the mailbox, not the sender. Compensating control today: review pending notices before relying on the totals. Fix tracked as MEJ-002.
  • Other boundaries in the code: the trigger token can only start a pass (it never reads data); provider error text is not persisted (fixed strings in ingest_runs); quarantine stores locators and reason codes, never bodies; credential files must be owner-only or they are rejected.
  • Closed on branch claude/fix-endurecimiento-seguridad (not merged): /api/fx-rate now requires a session and the proxy no longer skips api* paths (MEJ-006); ?error= carries fixed codes, not free text (MEJ-007).

Known constraints & security notes

  • Private self-hosting over Tailscale, not public Internet exposure. Still use a strong, stable BUDGETSPIN_AUTH_SECRET (changing it invalidates sessions) and a strong password.
  • Never commit .env.production. No secrets or personal data in the repo (it is public) — see the PII rule in CLAUDE.md.
  • Single instance behind Traefik; migrate-on-start is fine for one replica. Multi-instance would need migrations as a separate step (Phase 6).
  • If ever exposed beyond Tailscale: add HTTPS, stricter headers, and 2FA (currently future work).
